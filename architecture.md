# Architecture & Technical Design - Smart Event Management System

## 1. System Overview
The system is built using a Python Flask backend, structured around clean architecture principles, and integrates advanced AI agents with cloud persistence.

## 2. Backend & Architecture Patterns
* **Framework:** Python Flask (handling routing, business logic, and API endpoints).
* **Architectural Pattern:** MVC (Model-View-Controller) / CQRS (Command Query Responsibility Segregation) to separate data reads from state-changing commands (e.g., booking seats, submitting talks).
* **Event Sourcing:** Every talk state change is appended immutably to `stored_events` (`TalkProposed`, `TalkInnovationReviewed`, `TalkApproved`, `TalkRejected`, plus related domain events). `cqrs/projections.py` rebuilds current talk state by folding that stream. Organizers inspect the chronological audit trail on the dashboard Event Log (`GET /api/organizer/event-log`). The Event Log WHEN column always renders English timestamps (`en-US`, e.g. `Oct 13, 2026, 10:15 AM`). Speakers see declined proposals in Your Submissions → Rejected Proposals.

## 3. Database & Cloud Persistence
* **Relational Database (Cloud):** Hosted on **Somee.com** (SQL-based cloud hosting) to manage core entities: Users (Organizers, Speakers, Attendees), Events, Sessions, and Bookings.
* **Vector Database (RAG):** Talk titles, abstracts, and speaker bios are embedded and stored as JSON vectors in `talk_embeddings` (Somee / SQL). A local hashing embedder is used for semantic search (`/api/search`, organizer, and attendee routes).

## 4. AI & MCP Integration
* **Autonomous Deep Agent:** `services/deep_agent.py` scans pending talk proposals on submit and on a background interval (also `python scripts/run_assessment_agent.py`). It acts as an Innovation & Uniqueness Reviewer: RAG compares the new title/abstract against all approved and pending talks, then stores `innovation_score`, `innovation_badge`, overlapping talks, and a uniqueness explanation on `talk_submissions.ai_assessment` (also surfaced on the proposal payload). Recorded as a `TalkInnovationReviewed` event.
* **AI Innovation Ideas Hub:** Speakers search any topic (`POST /api/speaker/innovation-ideas` with `query`) and local Ollama (`services/idea_hub.py`, `POST http://127.0.0.1:11434/api/generate`, model `llama3` or `OLLAMA_MODEL`) drafts tailored talk concepts. Empty search shows the trending board. Offline or empty Ollama responses fall back to curated ideas for that topic.
* **Abstract enhancer:** `POST /api/speaker/enhance-abstract` sends a short draft to local Ollama (`num_predict: 100`, `temperature: 0.3`, `num_ctx: 512`, 9s generation budget). Generation streams and stops after two finished sentences or the wall-clock deadline so the abstract can render in the speaker UI within 10 seconds. A background warmup keeps llama3 loaded (`keep_alive: 30m`). If Ollama is offline or times out, the original draft is returned unchanged so the speaker UI does not crash.
* **Vector DB / RAG:** `compare_against_program` ranks the proposal against the full approved/pending catalog so high overlap lowers novelty and unique angles raise the Innovation Score.
* **Model Context Protocol (MCP):** An in-process MCP server/client (`mcp/`) exposes tools the Deep Agent can invoke. `tavily_web_speaker_search` runs a live Tavily query of speaker name + talk title (`services/tavily.py`, `TAVILY_API_KEY`) and stores snippets on the proposal. Pending Proposals cards do not show a Tavily badge; they keep Innovation Score, uniqueness, and overlap chips only. `venue_capacity_validator` checks hall sizes (50/100/300) and schedule conflicts. `python scripts/run_mcp_server.py` serves the same tools over stdio JSON-RPC. Pytest stays offline.

## 5. Attendee Hall Seating
* **Layout:** `services/seating.py` builds a grid from hall capacity. Named halls in `HALL_LABELS` are Conference Room (50 seats, 5×10), Grand Hall (100 seats, 10×10 with a mid-house cross-aisle only), and Main Auditorium (300 seats, 15×20 in Left / Center / Right blocks with a mid-house cross-aisle). Seat labels use IDs such as `A1`. Forms, tables, and seat maps render `hall_label` as the hall name plus capacity.
* **Session length:** `normalize_schedule` accepts start times on 30-minute marks only (`08:00`–`22:00`) and always stores `end_time` as start plus 90 minutes. Organizer invite and speaker proposal forms share `partials/session_time_fields.html`: a start-time dropdown and a read-only end-time display. Date fields share `partials/date_picker.html`, a custom calendar (hour-and-half-hour times stay on the time dropdown). Action buttons use a shared `.btn-busy` spinner while a request is in flight. Status banners (`#status`, form alerts) auto-dismiss after 6 seconds with a fade-out.
* **Read model:** `GET /api/attendee/events/<id>/seats` returns the map plus taken IDs from confirmed bookings.
* **Command:** `RegisterAttendee` accepts `seat_ids`, rejects unknown or already reserved seats, stores them on `bookings.seat_labels`, and increments `events.seats_booked`. Quantity-only bookings auto-assign the next open seats. `SeatReserved` includes the seat IDs.

## 6. Event program states
* Approved events stay on the attendee catalog. Remaining seats drive a **LAST SEATS** ribbon (1–10 open) and **Sold Out** (0 open).
* `events.status` also stores `cancelled` and `deleted`. Attendee browse and **My Events** hide both. `GET /api/organizer/events` and `GET /api/speaker/events` return only `approved` / `active` sessions. `POST /api/organizer/events/<id>/cancel` and `POST /api/speaker/events/<id>/cancel` cancel an approved event, refund confirmed bookings, move the session to Trash / Recycling Bin (`status=cancelled`), and write automated chat notices. Admin cancel notifies the lecturer; lecturer cancel notifies the organizer; ticket holders always receive a refund notice. Lecturer and organizer chat live in matching right-side sidebars (`#speaker-chat-sidebar`, `#organizer-chat-sidebar`) with a green unread-count badge on the chat icon. The organizer inbox (`GET /api/organizer/messages`) groups threads by lecturer and titles each row with `peer_name`. Opening a conversation shows the email-style history and an empty compose box; `POST /api/speaker/messages` and `POST /api/organizer/messages` send only the text the user typed. `GET /api/organizer/trash` includes rejected proposals and cancelled events. Permanently deleting a cancelled event sets `status=deleted`. `DELETE /api/organizer/events/<id>` is a soft delete (`status=deleted`) rather than a hard row remove.
* Organizer and speaker **More Details** open a cinematic modal that shows only the lecture summary (abstract). Hall, seats, and AI uniqueness metadata stay on the table row, not in the popup.
* `python scripts/seed.py --reset` (or `flask --app main seed`) loads a realistic program covering open, last-seat, sold-out, cancelled, and deleted sessions.
