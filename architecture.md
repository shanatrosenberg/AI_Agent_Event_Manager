# Architecture & Technical Design - Smart Event Management System

## 1. System Overview
The system is built using a Python Flask backend, structured around clean architecture principles, and integrates advanced AI agents with cloud persistence.

## 2. Backend & Architecture Patterns
* **Framework:** Python Flask (handling routing, business logic, and API endpoints).
* **Architectural Pattern:** MVC (Model-View-Controller) / CQRS (Command Query Responsibility Segregation) to separate data reads from state-changing commands (e.g., booking seats, submitting talks).
* **Event Sourcing:** Every talk state change is appended immutably to `stored_events` (`TalkProposed`, `TalkInnovationReviewed`, `TalkApproved`, `TalkRejected`, plus related domain events). `cqrs/projections.py` rebuilds current talk state by folding that stream. Organizers inspect the chronological audit trail on the dashboard Event Log (`GET /api/organizer/event-log`). The Event Log WHEN column always renders English timestamps (`en-US`, e.g. `Oct 13, 2026, 10:15 AM`). Speakers see declined proposals in Your Submissions → Rejected Proposals.

## 3. Database & Cloud Persistence
* **Relational Database (Cloud):** Hosted on **Somee.com** (SQL-based cloud hosting) to manage core entities: Users (Organizers, Speakers, Attendees), Events, Sessions, Bookings, and talk topics (`topics` catalog). The organizer adds catalog topics from speaker invitations; `ensure_topics_schema` seeds AI, Architecture, Community, and Product. Lecturer dropdowns and attendee Filter by topic read the same catalog.
* **Vector Database (RAG):** Talk titles, abstracts, and speaker bios are embedded and stored as JSON vectors in `talk_embeddings` (Somee / SQL). A local hashing embedder is used for semantic search (`/api/search` and attendee API routes). The public `/events` browse page keeps topic and speaker dropdowns plus Search and Reset Filters; it does not render the keyword search text field.

## 4. AI & MCP Integration
* **Autonomous Deep Agent:** `services/deep_agent.py` scans pending talk proposals on submit and on a background interval (also `python scripts/run_assessment_agent.py`). It acts as an Innovation & Uniqueness Reviewer: RAG compares the new title/abstract against all approved and pending talks, then stores `innovation_score`, `innovation_badge`, overlapping talks, and a uniqueness explanation on `talk_submissions.ai_assessment` (also surfaced on the proposal payload). Recorded as a `TalkInnovationReviewed` event.
* **Abstract enhancer:** `POST /api/speaker/enhance-abstract` sends a short draft to local Ollama (`num_predict: 100`, `temperature: 0.3`, `num_ctx: 512`, 9s generation budget). Generation streams and stops after two finished sentences or the wall-clock deadline so the abstract can render in the speaker UI within 10 seconds. A background warmup keeps llama3 loaded (`keep_alive: 30m`). If Ollama is offline or times out, the original draft is returned unchanged so the speaker UI does not crash.
* **Vector DB / RAG:** `compare_against_program` ranks the proposal against the full approved/pending catalog so high overlap lowers novelty and unique angles raise the Innovation Score.
* **Model Context Protocol (MCP):** An in-process MCP server/client (`mcp/`) exposes tools the Deep Agent can invoke. `tavily_web_speaker_search` runs a live Tavily query of speaker name + talk title (`services/tavily.py`, `TAVILY_API_KEY`) and stores snippets on the proposal. Pending Proposals cards do not show a Tavily badge; they keep Innovation Score, uniqueness, and overlap chips only. The Repeats / Overlaps Found popover is portaled to `document.body` with a fixed high z-index so later proposal cards cannot cover it. The bubble itself uses `max-h-48` and `overflow-y-auto` so long overlap lists scroll instead of clipping. `venue_capacity_validator` checks hall sizes (50/100/300) and schedule conflicts. `python scripts/run_mcp_server.py` serves the same tools over stdio JSON-RPC. Pytest stays offline.

## 5. Attendee Hall Seating
* **Layout:** `services/seating.py` builds a grid from hall capacity. Named halls in `HALL_LABELS` are Conference Room (50 seats, 5×10), Grand Hall (100 seats, 10×10 with a mid-house cross-aisle only), and Main Auditorium (300 seats, 15×20 in Left / Center / Right blocks with a mid-house cross-aisle). Seat labels use IDs such as `A1`. Forms, tables, and seat maps render `hall_label` as the hall name plus capacity.
* **Session length:** `normalize_schedule` accepts start times on 30-minute marks only (`08:00`–`22:00`) and always stores `end_time` as start plus 90 minutes. Organizer invite and speaker proposal forms share `partials/session_time_fields.html`: a custom start-time popover (clock icon, half-hour slots, portaled menu) and a matching read-only end-time display. Date fields share `partials/date_picker.html`, a custom calendar (hour-and-half-hour times stay on the time popover). Action buttons use a shared `.btn-busy` spinner while a request is in flight. Status banners (`#status`, form alerts) auto-dismiss after 6 seconds with a fade-out.
* **Read model:** `GET /api/attendee/events/<id>/seats` returns the map plus taken IDs from confirmed bookings. When the caller is a signed-in attendee, owned seats from their confirmed booking are listed in `owned` and each seat includes `owned: true`.
* **Command:** `RegisterAttendee` accepts `seat_ids`, rejects unknown or already reserved seats, stores them on `bookings.seat_labels`, and increments `events.seats_booked`. Quantity-only bookings auto-assign the next open seats. `SeatReserved` includes the seat IDs. A second purchase for the same attendee and event is an additional order: owned seats are rejected (`you already hold seat(s)`), new labels are appended to the existing confirmed booking, and `AdditionalSeatsPurchased` is appended. The ticket modal shows owned seats in green and disables them so they cannot be re-selected. `CancelAttendeeRegistration` lets the booking owner release one or more confirmed seat IDs, or the whole registration, only when at least 48 hours remain before `event.date` + `event.start_time`. A partial cancel updates `bookings.seat_labels` and `bookings.seats`, decrements `events.seats_booked` by the released count (not below 0), and appends `SeatReleased`. Cancelling the last seat (or omitting `seat_ids`) sets `bookings.status` to `cancelled` and also appends `BookingCancelled`. Confirmed bookings only count toward taken seats and My Tickets. `POST /api/attendee/tickets/<booking_id>/cancel` is attendee-auth only and accepts optional `seat_ids`; requests inside the 48-hour window return 403 with the policy message.
* **Waitlist agent:** Sold-out sessions store `waitlist_entries` (`JoinWaitlist`). A client cancel that re-opens seats calls `notify_seats_released`, which broadcasts a `waitlist_offer` notice to every waiting attendee. `ClaimWaitlistSeats` is FCFS: it assigns the next open seats through `RegisterAttendee`, capped at `min(requested, remaining, original waitlist size)`, then marks the entry claimed. A later claimant receives 409 when no seats remain. Admin event cancel marks remaining waitlist rows cancelled.
* **Group seating agent:** `services/group_seating.py` (`suggest_group_seats`) is optional and used only when a client asks to be seated together. `POST /api/attendee/events/<id>/group-seats` accepts `{seats: N}` for N≥2. A request larger than `remaining_seats` returns 409 and does not select seats. Otherwise the agent searches compact rectangles inside one vertical-aisle section and one cross-aisle band, scoring shorter blocks toward the front and center. If no such block exists, it returns nearby row-runs with `mode=dispersed` and `needs_confirm=true` so the ticket modal can prompt before applying the layout. Dismissing the agent leaves manual seat clicks unchanged. Quantity-only `RegisterAttendee` still uses first-N leftover seats.

## 6. Event program states
* Approved events stay on the attendee catalog. Remaining seats drive a **LAST SEATS** ribbon (1–10 open) and **Sold Out** (0 open).
* `events.status` also stores `cancelled` and `deleted`. Attendee browse and **My Events** hide both. `GET /api/organizer/events` and `GET /api/speaker/events` return only `approved` / `active` sessions. `POST /api/organizer/events/<id>/cancel` cancels an approved event, refunds confirmed bookings, moves the session to Trash / Recycling Bin (`status=cancelled`), and writes automated chat notices. Lecturers have no cancel or cancel-request UI. `POST /api/speaker/events/<id>/cancel` and `POST /api/speaker/events/<id>/cancel-request` return 403. Admin cancel notifies the lecturer; ticket holders always receive a refund notice. Lecturer and organizer chat live in matching right-side sidebars (`#speaker-chat-sidebar`, `#organizer-chat-sidebar`) with a green unread-count badge on the chat icon. The organizer inbox (`GET /api/organizer/messages`) groups threads by lecturer and titles each row with `peer_name`. Opening a conversation shows the email-style history and an empty compose box; `POST /api/speaker/messages` and `POST /api/organizer/messages` send only the text the user typed. `GET /api/organizer/trash` includes rejected proposals and cancelled events. Permanently deleting a cancelled event sets `status=deleted`. `DELETE /api/organizer/events/<id>` is a soft delete (`status=deleted`) rather than a hard row remove.
* Organizer and speaker **More Details** open a cinematic modal that shows only the lecture summary (abstract). Hall and AI uniqueness metadata stay on the table row, not in the popup. The Open/Sold Seats column and counter stay on the organizer dashboard only; lecturer My Events omits them after a frontend `data-user-role` check.
* Attendee / client signup (`/register?role=attendee`, browse Join, and Buy Tickets new-customer) collects User Name and Password only. Display name is omitted; the stored name defaults to the user id. Speaker registration still includes Display name.
* `python scripts/seed.py --reset` (or `flask --app main seed`) loads a realistic program covering open, last-seat, sold-out, cancelled, and deleted sessions.
