# System Requirements Document (SRD) - Smart Event Management System

## 1. Introduction
This document defines the functional and non-functional requirements for the **Smart Event Management System**, developed under the Specification-Driven Application Development (SDAD) methodology.

## 2. System Actors & Roles
The system supports three primary user roles:
1. **Event Organizer (Admin):** Manages event schedules, creates sessions, maintains the shared topic catalog from speaker invitations, views dashboards and the Event Log / audit trail, reviews automated AI assessments for talk submissions (approving or rejecting proposals), and can cancel an approved event.
2. **Speaker:** Registers in the system, submits talk proposals (including titles, abstracts, and bios), chooses a catalog topic or Other for a one-off unlisted label on that talk only, tracks proposal statuses, and sees only approved events in My Events. Lecturers cannot cancel events or request cancellation.
3. **Attendee:** Browses upcoming sessions, filters by topic or speaker, views data in clean tabular views, books or reserves seats for events, and opens My Tickets to see booked sessions as cards. From that view the client can cancel an individual seat or all remaining seats when at least 48 hours remain before the session starts. When a session is sold out, the client can join a waitlist and later claim freed seats first-come, first-served.

## 3. Functional Requirements
1. **Authentication & User Management:** Secure user registration and login with distinct role-based permissions (Organizer, Speaker, Attendee). Client-facing login and account identifier fields are labeled **User Name**. Attendee / client registration uses User Name and Password only (no Display name field).
2. **Data Search & Details:** 
   * The attendee events page lists the upcoming program (closest date first) with topic and speaker dropdowns, a Search button, and Reset Filters. The keyword search text field is not shown. Topic filters include every admin-saved catalog topic, plus topics already shown on public event cards.
   * The system must allow viewing detailed information for any selected result. Keyword search remains available on API routes used by organizers and internal ranking.
3. **Tabular Data Views:** System data (such as session schedules, booking lists, and user directories) must be presented in structured tables. Organizer My Events tables match the Approved events columns (Event, Speaker, Date, Time, Hall, Open/Sold Seats, Status). Lecturer My Events uses the same columns except Open/Sold Seats, which is hidden for the lecturer role. Date and Time columns stay on one line (`2026-10-08`, `21:59–23:59`) with extra width and padding. Lecturer Your Submissions, Rejected Proposals, and Organizer Requests use the same Date/Time treatment. More Details opens a cinematic modal that shows only the lecture summary (abstract).
4. **Management Dashboard:** A dedicated dashboard displaying key metrics, such as open sessions, total registrations, and seat capacity.
5. **Data Entry (Command Model):** Authorized users can input new data, such as booking a seat, submitting a talk proposal, or creating a new session. The organizer adds catalog topics from the speaker-request form (`GET`/`POST` `/api/organizer/topics`). The new-topic input and Add topic button stay hidden until the admin chooses **+ Add new topic**. A new topic is stored in `topics` immediately and appears in later admin invitations, lecturer topic dropdowns, and attendee Filter by topic. Lecturers cannot add catalog topics (`POST /api/speaker/topics` is forbidden); they pick a listed topic or Other for a one-off label on that proposal only. The organizer dashboard has no standalone Topics tab. Organizer and lecturer schedule pickers allow start times on the hour or half-hour only; the end time is set automatically to 90 minutes later and is not edited by hand. Start-time fields use a custom time popover (clock icon, grouped half-hour slots) instead of a native dropdown; the end-time field uses the same visual treatment and stays read-only. Date fields use a custom calendar styled to the product palette (rounded days, hover and selected states). Action buttons show a spinner while the request is processing. Status banners and action alerts fade out automatically after 6 seconds. Only the organizer can cancel an approved event; the session is removed from the active program immediately and moved to Trash / Recycling Bin (`status=cancelled`). Ticket holders receive an automated chat notice that the event is cancelled and a full refund will be issued. Lecturers have no Cancel Event or Request Cancellation action. `POST /api/speaker/events/<id>/cancel` and `POST /api/speaker/events/<id>/cancel-request` are forbidden. Lecturer and organizer dashboards share a two-way chat: a green unread-count badge sits at the top-right of the chat icon, opening the panel shows an email-style thread, and either side can type and send a custom reply. The organizer inbox lists one conversation per lecturer, titled with that lecturer's name rather than a generic cancellation heading. An admin cancellation notifies the lecturer. Organizer and lecturer More Details views show only the lecture summary (abstract).
6. **Autonomous AI Assessment Agent:** A background process reads speaker submissions, queries a vector database (RAG style), and performs external checks via MCP tools (e.g., Tavily search) to evaluate talk relevance.
7. **Hall Seat Selection:** When booking a session, attendees see a visual seating map sized to the named hall (Conference Room 50, Grand Hall 100, Main Auditorium 300), click available seats to select or deselect them, and reserve those seat IDs. Taken seats are disabled; the booking updates remaining capacity. A client who already holds tickets for an open session can buy more from Browse (`Buy more tickets`) or My Tickets (`/events?buy=<event_id>`). The seat map highlights that client's existing seats in green (`owned`), those seats cannot be selected again, and `RegisterAttendee` appends only newly chosen seats to the confirmed booking. Re-submitting an owned seat returns 409. An optional Smart Group Seating Agent can suggest seats for a group of 2 or more (`POST /api/attendee/events/<id>/group-seats`). It first checks remaining inventory and blocks the request with a clear “not enough places available” message when the group is larger than remaining seats. If inventory is sufficient it looks for a compact block that stays inside one aisle section and house band, preferring short rectangles over a long single line. When a single block is not available but enough seats remain, it suggests the closest adjacent seats (for example two nearby rows) and asks the client to accept that layout before applying it. The agent is never required: the client can dismiss it and keep picking seats one by one. Hall pickers and tables show the hall name with capacity in parentheses. Logged-in clients open My Tickets (`/my-tickets` and `/my-events`) to see each booked session as a card listing the specific seat IDs. A client may cancel one seat, several seats, or the whole registration only when the current time is at least 48 hours before the session start (`POST /api/attendee/tickets/<booking_id>/cancel` with optional `seat_ids`). If fewer than 48 hours remain, per-seat Cancel ticket actions are hidden and the card explains that cancellations are only allowed up to 48 hours before the event. A partial cancel removes those IDs from `bookings.seat_labels`, lowers `bookings.seats` and `events.seats_booked`, and re-opens the released seats. Cancelling the last seat marks the booking cancelled and removes the card. Sold-out sessions show **Join Waitlist** with a plus/minus seat counter (1–10, or hall capacity if smaller). `POST /api/attendee/waitlist` records the request. When a cancellation frees seats, the waitlist agent notifies every waiting client (`waitlist_offer` chat on My Tickets) with a **Claim seats** action and quantity stepper capped at the freed count or the original request. `POST /api/attendee/waitlist/<event_id>/claim` is first-come, first-served: the first successful claim assigns the next open seats and updates `seats_booked`; later claims fail if nothing remains.

## 4. Non-Functional & Architecture Requirements
1. **Methodology:** Developed using structured Markdown documentation and SDAD.
2. **Framework & Architecture:** Built on a **Flask** application server, structured with **MVC / CQRS** patterns, and implementing **Event Sourcing** for state management.
3. **Database & Deployment:** Data persistence managed via a cloud database (e.g., Somee.com).
4. **AI & MCP:** Integration with a vector database for semantic matching and external tool integration via **Model Context Protocol (MCP)**.
5. **Version Control:** Fully tracked and managed in a GitHub repository.
6. **Development Standards:** Clean, modular Flask/CQRS code, descriptive commits, and a polished professional UI/UX.
